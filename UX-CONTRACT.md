# Frontend interaction contract

Authority: the user's chat requirements and the read-only API definitions inspected in D:/YOLO/app/server.py and config.py. The approved React frontend is integrated into the main project. Source is frontend/; its production build is app/static/. The old frontend and token generator are removed. Model training and automatic live recording remain outside this frontend task.

On startup, connect to the local engine with read-only status/settings/camera requests. Camera capture starts only through Start detection. A stopped/offline source has an honest empty panel; both camera canvases request /api/frame/upper and /api/frame/lower with one request in flight per view and contain no sample photos or simulated boxes. Settings edits remain in memory during a service outage; saving is disabled until the service recovers. There is no frontend-disconnect or browser-only settings mode. Production runs on 127.0.0.1:8876 through the existing Python launcher and serves compiled assets under /static. The optional frontend development server proxies /api to the same backend. Runtime does not require Node.js.

Live polls status without overlapping requests and clears real evidence on loss; it never falls back to synthetic preview while connected. No prediction means Not visible. Visible wrist accessories are a violation. No worker identity, eligibility or stored live video. Live contains no synthetic boxes or personnel figures. Only the Sample dashboard uses synthetic numbers. The four main-screen metric slots are explicit Coming soon placeholders with em-dash values for total workers detected, violations, violation percentage, and workers currently in Camera 1. The user deferred person tracking and counting; no totals, zeros, or percentages are fabricated. A disconnected source cannot turn the other category green.

Test supports upper/lower/both, images and videos up to 250MB. Preview source files use browser object URLs and are revoked on removal/unmount. Only Run detection sends the file. Busy and processing prevent duplicate submission. Stop & remove aborts upload then requests backend cleanup. Every processed video automatically produces silent H.264 MP4, temporary until next test/removal/service exit. The completed result switches from still-frame previews to a video player using /api/test/{id}/video, with byte-range seeking. Download uses /api/test/{id}/download. Both routes require the current completed job. JPEG previews remain in memory under the media lock, avoiding Windows preview-file replacement races. Selecting a new file suppresses previous-job polling until a new run starts. A lost API clears download/result evidence. No fabricated inference in preview mode.

Settings draft is separate from saved values. Settings always save through PUT /api/settings and are blocked while live/media runs or the service is unavailable. Save announces success, stays on Settings and preserves draft on failure. Same camera can serve both views; either may be disabled. Native Windows driver queries expose supported picture controls, actual minimum/maximum/increment/default and automatic/manual modes. Unknown controls are hidden and guessed limits are not accepted. Saves and camera starts validate fresh capabilities; custom profiles carry a physical-device identity. Camera defaults mean the driver's reported defaults. Manual exposure/focus disables its automatic mode; enabling automatic mode clears the conflicting manual request. Initial and effective values are read from the driver when available. Refresh camera controls is available while stopped. Saved profiles apply on next connection. Upper SAHI, YOLO input sizes and existing ROI/model-specific fields are preserved.

Navigation guards unsaved changes with a named native modal and safe initial focus. Escape/stay preserve edits; discard explicitly loses draft. Reload uses the browser's standard unsaved-document guard. The integrated application connects automatically; no operator disconnect control is shown. Main navigation has hash links and aria-current. Keyboard, visible focus, a narrow viewport, native popup open/close, offline, and error recovery are verified in the integrated production browser harness.

Latest layout decision: Live fills the content width beside the navigation rail, removing the landscape max-width gutters. The bottom connection and fullscreen icons are removed from the sidebar. Main theme, cards and artwork stay unchanged.

Live metrics remain placeholders in stopped, running, offline, and stale states until counting is implemented. Settings > Inference & hardware displays the GPU name, CUDA readiness, and per-model inference milliseconds and measured processing FPS from the existing status API. Camera captions retain measured preview/detection rates; stopped/stale views clear the rate. Each preview draws at most 20 frames per second, skips duplicate sequence IDs and fetches only the latest published JPEG. HTTP 204 means no usable frame and hides the canvas; failed requests time out and retry without a backlog. Live footage uses object-fit: contain inside fixed responsive panels, preserving the entire frame without distortion. Changing resolution, frame aspect ratio, or waiting/retry state does not resize the panel. Both camera feeds remain stacked, the larger 16:10 upper-camera panel above the smaller 16:6 lower-camera panel, at every viewport width, with natural document scrolling. Current one-camera laptop testing shares its physical camera across both logical views.

Camera capture, preview publishing and YOLO inference run independently. The preview worker always renders the newest captured frame, optionally drawing the latest detection boxes while their source frame is less than one second old. YOLO only processes the newest frame and does not encode the live video. The finite HTTP frame endpoint only reads published JPEGs, so neither inference nor JPEG encoding runs in the HTTP event loop. A connected camera keeps its canvas during slow inference and shows UPDATING with delayed-results text; stale detections still clear to Not visible. Preview FPS is measured separately from detection FPS. A real disconnect or Stop clears the preview. Starting/stopping clears pending images and results; a stopped worker cannot publish an old result into a later session.

Earplugs appear as a fourth PPE status card with a permanent neutral IN PROGRESS label in all connection and detection states. They do not read upper/lower summaries or imply supported earplug detection. The selected option C crossed-out-watch icon appears in both wrist locations. Clear Wrists and Wrist Accessories labels and all detection rules remain unchanged.

The former MJPEG route and stream retry component are removed. The capture worker negotiates native driver format, tolerates brief empty startup reads, converts grayscale/BGRA to BGR, and reopens a source after repeated failed reads. Stop cancels pending preview requests. No invalid/placeholder JPEG is represented as a live frame.

The public UI name is AI Based PPE Monitoring & Warning across headings, page titles, and navigation. The exact tagline is Safety First,No Harm to ANYONE. Existing launcher filenames and the preserved industry ZIP retain their names. Date/time, system status, and the detection action share one header row, in that order. The GPU name appears in Settings only. The legacy internal health identifier remains ppe-guard for service/stop compatibility. Supplied goggles and Bekaert files retain their original pixels; brand asset provenance is recorded in branding/sources.json. A compact, wide footer places the full team names between the logos on desktop: Ridham Chhajer, Kedar Naygaonkar, Kedar Pethkar, Sanskruti Chaure, Sahil Nehate, Om Parmar. On mobile the names move below the logo row. Footer logos preserve their aspect ratios at narrow widths.

Each PPE card exposes its actual observation state as data-status. DETECTED uses a green card background; violations use red. NOT VISIBLE and earplug IN PROGRESS stay neutral, including when stopped, disconnected or stale. Card and pill text must maintain at least 4.5:1 contrast in active states.

Local camera compatibility: each native camera handle lives in a dedicated process; calls have deadlines, and Stop terminates a blocked owner after a short graceful wait. Only that camera child is targeted. Shared-memory frames are copied before publication. Driver limits are validated before capture; effective control values use read-back without opening a second driver graph while capture owns the device. This local change is excluded from the industry package.

Per-camera Expand controls use the native Fullscreen API on the existing viewport, retaining the same canvas, telemetry, and frame requests. A labelled exit button or Escape restores normal layout. Fullscreen errors appear inside the viewport. Source resolution changes update canvas backing dimensions only. Browser zoom remains enabled; both feeds stay stacked at every zoom level, with scrolling as needed and no clipping.
